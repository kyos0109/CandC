# Version 3 discussion and moderator contract

> **Implementation status:** This revision includes the opening, interim-result,
> optional-claim and associated prompt/invitation/control rules below. See the
> [implementation comparison](IMPLEMENTATION_STATUS.md) for historical behavior and
> validation limits; prompt expectations do not guarantee model quality.

For setup, everyday controls and result interpretation, see the [user guide](USER_GUIDE.md).
This document owns the exact version 3 rules; the guide and README summarize them.

## Option evaluation v1

New v3 rooms may explicitly select `kind=selection` with `selection:{version:1,optionCount:2..6}` (default count 4). They require conclusion mode, 2–4 seats, no moderator, no active discussion policy and no research/roots. The first seat generates the options and exactly three equally weighted criteria; all configured seats then evaluate every option/criterion with integer scores 0–10 and reasons. Higher always means better fit. Each call uses a new native session and workspace, no prior messages, and only the frozen topic/goal/constraints, that seat's instructions and the common option set. Ratings and generation history never enter later reviewer prompts, including for repeated providers or the generating seat.

`room.selection` owns generating/scoring/complete phases, the option set identified by its generation call ID, per-seat ratings with call provenance and the final ranking. Valid structured actions are `selection-options` and `selection-rating`; call purposes have the same names. Public answer, validated payload and completed call commit together. Missing/duplicate/unknown matrix entries, incorrect set identity, invalid scores or reasons, wrong option count or duplicate option titles/IDs pause without counting the response. Public fallback text remains saved. No automatic retries, fabricated zero scores or reduced reviewer roster are allowed.

After every seat has a confirmed valid rating, the controller commits the deterministic ranking: total divided by three times reviewer count. Sort by exact integer totals, display two decimals, retain original option order for ties and assign shared competition ranks. There is no extra model synthesis or tiebreaker. This is a model evaluation result, never a participant consensus or moderator ruling; proposal/outcome remain null. Incomplete runs expose saved individual scores without a final ranking. JSON and Markdown export preserve options, criteria, scores, reasons, limitations and provenance.

The automatic sequence makes one generation and one call per seat under total/turn time limits; discussion round limits do not interrupt this finite sequence. Pause finishes the current call; stop aborts it. Explicit continuation fills missing work only. Uncertain provider outcomes require reconstruction, uncertain storage blocks all writes/scheduling until verified recovery and reconstruction. Frozen inputs cannot be edited or supplemented; create a new evaluation for changes. Only time limits may be adjusted without changing the task version. Completed evaluations cannot start again. Existing journals are not rewritten; rollback requires matching binary/journal versions because older strict schemas reject the new fields and purposes.

Version 3 is separate from the version 1/2 controller and schemas. `DiscussionService` routes histories by their immutable behavior version and admits only one active discussion across both controllers. New records use compact journal format 4; opening a mixed directory does not migrate older records. Storage remains the authoritative journal with append, sync and close before updating memory or emitting a committed event. Any uncertain append blocks scheduling and further journal writes until explicit verified recovery.

## Participants and provider boundary

A room has 2–4 speaker seats and zero or one moderator (`moderator`). A seat is one independent speaking session. Its ID (`^[a-z][a-z0-9-]{0,23}$`, never `moderator`, `user`, `all` or `both`) is not its provider, so several seats may use the same provider. The first seat of a provider normally keeps the provider's ID (`codex`); later ones use `codex-2`, `codex-3`. An optional `label` (at most 40 characters) names the seat in the UI and in the moderator roster. Each seat and the moderator has its own provider, model/effort selection, native session ID and UUID generation. The workspace is `.cache/agents/rooms/<discussion>/<seat>/<generation>`. Seats of one provider never share a native session (the cross-owner collision check is keyed by provider and native ID), and a private message to one seat is delivered to no other seat, including another seat of the same provider. Mute, speak, proposal confirmation and recipients all refer to seat IDs. A moderator can use a speaker's provider/model; it cannot use that speaker's native session or fork it. Cross-owner native session collisions are rejected using historical call provenance. Cancellation retires that owner's session; subsequent generation uses confirmed eligible history. Summary calls always use a fresh generation and do not update ordinary sessions or declare completion.

Demonstration sessions hold their memory only in the adapter process. Loading a saved idle demonstration room does not rewrite its journal or invoke any adapter. Its first explicit start after controller initialization retires saved fake session identities in the start commit; each owner then receives a new generation and its complete eligible confirmed history. This does not change live session resumption or permit stopped/indeterminate rooms to bypass explicit reconstruction.

The common `AgentAdapter`/`TurnRequest` interface is shared; invocation and JSON protocols are native per provider:

| Provider | Invocation and session | Application readiness |
| --- | --- | --- |
| Codex | Existing app-server RPC; explicit thread/start or named thread/resume; effective configuration and no-tool/MCP policy verified by the established adapter | Installed pinned CLI, ChatGPT subscription login, catalog model/effort validation |
| Claude | Existing safe noninteractive stream-json path; named resume; tools/init model checked | Installed pinned CLI, claude.ai subscription login, explicit model/effort |
| Gemini | Headless stdin, stream-json init/message/result, explicit model/named resume; unexpected tools/model/session/error fail closed | Live locked: no installed CLI/auth/effective zero-tool policy validation in this delivery |
| Grok | Official grok CLI streaming-json; owned prompt file removed after cleanup; named UUID creation/resume; tool denials, modelUsage and session checked; thought events discarded | Live locked: no installed CLI/subscription auth/inherited hooks and MCP isolation validation in this delivery |

No API key fallback is enabled. Gemini/Grok protocol fixtures are not proof that login, inherited configuration, no-tool policy, cancellation or real resumption work. Do not unlock them merely because `--version` succeeds. The application returns per-provider readiness/reason and preflights only selected providers. New providers do not advertise invented model catalogs or configurable reasoning levels. Their demonstration seats exercise scheduling with fake adapters only.

Readiness states are `missing`, `start-failed`, `unverified`, `login-required`, `auth-check-failed` and `ready`. Version probes distinguish a missing executable from a failed or timed-out launch; failed output cannot establish a version. Authentication diagnostics recognize known subscription-login results without returning raw process output. Live creation cards show status and a connection/recheck entry even for unselected seats, and disable unavailable provider settings. The moderator uses the same readiness hints. CLI processes launch on demand; users do not need to keep a CLI terminal running. Demonstration mode does not require CLI readiness.

Primary protocol references: [Gemini headless](https://geminicli.com/docs/cli/headless/), [Gemini stream types](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/output/types.ts), [Grok official headless guide](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/14-headless-mode.md). Revalidate these against an installed, pinned version before enabling live inference.

## Input, delivery, response and privacy

Before launching, save a call snapshot: participant/provider/generation, requested settings, native resume identity, taskVersion/grantId, eligible message IDs, task/topic/goal/constraints, provisional draft boundary when monitoring, serialized input characters/hash and timeout reservation. Only completed eligible messages enter a native session. A successful validated completion commits the public answer, call result and delivery receipt together. The receipt includes its own public answer, preventing retransmission. Failed/cancelled/indeterminate text and uncommitted drafts never enter confirmed history. Actual prompt size is capped at 1,000,000 characters; no automatic truncation or summarization substitutes for oversized history.

Codex RPC rejections retain optional `RoomCall.providerFailure` and matching error-event metadata: the fixed provider, an allowlisted RPC method, a safe integer error code and a fixed reason (`active-writer`, `thread-not-found`, or `rejected`). Raw provider error messages/data and stderr are never persisted. Only exact recognized session-error messages establish the specific reason. A rejected `thread/start` or `thread/resume` records `turnRequestSent: false`; it creates no empty indeterminate answer. Other failures do not assert that submission was prevented. The room remains blocked as `indeterminate` until explicit session reconstruction, while the pause notice and diagnostics distinguish a turn that was not submitted from an unknown result. Reconstruction preserves saved history, clears native session bindings and returns to `paused`; a separate explicit start is required. It never retries an unknown-result call. New optional failure fields leave older records readable; rollback to an older strict-schema binary requires the matching journal/build pair.

For a pending proposal, `done` speakers are not repeatedly scheduled solely because confirmation is missing. A peer without a recorded review can still review the exact proposal; a reviewed peer can receive an unseen author response. Explicit review/repair requests, moderator invitations, runnable tasks, user input and bounded coverage/check redirects retain their priority. Once these are exhausted and the speakers are done, scheduling pauses with the proposal, peer-review gaps and dissent intact. A review with gaps still cannot confirm a proposal or create a final/interim outcome. Ordinary exchanges without a pending proposal retain their existing flow behavior.

Moderator input includes only `recipient=all` messages. Directed user inputs, private references, speaker role instructions and speaker-owned research evidence are excluded, including monitor and summary calls. An ordinary facilitator also receives the public proposal and speaker confirmation IDs; judges do not receive the proposal. Neither receives private request IDs. Completed public answers to directed inputs are public. The browser is the local user's view and may show their private messages; it is not the moderator's input. Call diagnostics and JSON exports are local user artifacts, not prompts. Research tools retain the existing read-only root restrictions; agent/cache/data/credential paths are blocked. Moderator calls currently have no research tools; this does not prohibit research authorized for speakers.

Optional response references are `{messageId, disposition: addressed|unresolved|checked, reason}`. They may cite only eligible input actually held in the owned session. Malformed reference arrays are rejected; unavailable references are filtered without crediting response coverage, while valid references remain. Rejected claims are recorded in optional `RoomCall.metadataDiagnostics`, independently of fatal `controlDiagnostic`. Saving public prose does not require accepting optional claims. Delivery alone does not credit response coverage. Results retain `unhandledRequests` IDs for user inputs without an explicit speaker addressed claim, including directed inputs. Those IDs are not exposed through moderator prompts. Response annotations represent model claims, not factual verification.

## Moderator authority and races

Output control is one final standalone `<<<CANDC_CONTROL_V3>>>` / `<<<END_CANDC_CONTROL_V3>>>` envelope outside Markdown fences and quotations, with strict JSON version/taskVersion/grantId/continuation/action. Speakers may use none/propose/confirm without a judge; judge speakers use none. Delivery metadata belongs in `action.delivery` for propose/judge finish; peer review belongs in `action.review` for confirm. The parser repairs the observed top-level `delivery` placement only when the action is propose/finish and no nested delivery field exists. Malformed optional work/references/delivery/review claims are rejected with metadata diagnostics, then the remaining core is strictly validated. When the core fails but the standalone envelope and JSON are valid, version is exactly 3, and typed taskVersion/grantId match the owned call, all control claims are discarded. The controller substitutes yield with speaker none or moderator observe and records `control-schema`; it does not infer a proposal, review, reference, work report or permission from the malformed payload. This also covers opening calls without replacing the reserved first speaker. Envelope/JSON/identity failures still preserve prose and pause without replay. Ownership, native-session, task/grant, provenance, authority and storage checks remain enforced. Valid but unauthorized speaker commands are rejected rather than neutralized. A malformed delivery cannot create a proposal or ruling; a malformed or mismatched review cannot confirm it. Judge-speaker propose/confirm is diagnosed as unsupported without applying a proposal. No saved answer is replayed or retroactively treated as an accepted proposal. Unknown targets, stale version/grant/draft and speaker-issued commands do not control scheduling.

Prompts are scoped to role and stage. Ordinary exchanges receive a short metadata layout and the meanings of continue (concrete unfinished contribution), yield (hand over) and done (wait for new content, not whole-discussion completion). Only a peer without its own saved review of the current proposal, or an actor with an explicit targeted delivery correction, receives the full delivery policy. A previously recorded acceptance or rejection suppresses repeated delivery policy/examples for that same proposal, while the proposal and reviews remain visible as discussion context. Replacement proposals have new IDs and reset reviews, restoring independent review instructions. Explicit peer confirmation repairs retain the supplied proposal identity and confirmation examples even when that peer already reviewed it; existence of a peer proposal and need for a new review are separate decisions. Peer review includes both acceptance and rejection layouts naming the supplied proposal ID, with neither verdict preferred; a correction includes its relevant proposal/ruling example. Ordinary facilitators never receive speaker delivery policy; judge speakers receive no unused propose/confirm examples. Debate speakers examine their assigned position and peer arguments while allowing justified revision; no minimum round count, compulsory opposition or domain template is imposed.

`moderatorMode` is `facilitator` (default) or explicitly selected `judge`. An ordinary facilitator can only observe or invite a speaker with speak. Its interrupt/mute/unmute/topic/pause/finish commands are saved as rejected (`judge-mode-required`) without applying them. Speakers lead the substance and use ordinary scheduling, including peer proposal confirmation and active-policy work when enabled. Before the first discussion turn, the application reserves the scheduled speaker and calls the facilitator for a neutral opening of at most two short sentences introducing the original topic, supplied goal and public roster, then handing over to `openingSpeaker`. This optional call field records the selected speaker durably; the opening can only observe, so a different invitation cannot replace the reserved first speaker. Private role instructions and directed inputs remain excluded. Opening text is prompted, not synthesized as a user/model claim by the application.

Opening is only attempted before any non-summary call or saved speaker discussion exists; its saved attempt prevents repetition on pause/resume, reload, additional input and session reconstruction, including uncertain calls that cannot be replayed automatically. Existing started/explicitly upgraded histories do not gain a retroactive opening. Summary-only calls do not consume this opportunity. Opening counts toward moderator/time budgets, never speaker contributions or consensus. User pause/stop during opening prevents the reserved speaker from starting. Judge scheduling remains unchanged.

There are no draft monitoring calls in ordinary mode. Following the opening, the facilitator is called once after a full speaker-count round or a speaker-confirmed outcome, subject to user pause/stop, status and execution budgets. An exhausted moderator-call budget skips coordination and does not block speaker continuation. Routine coordination is prompted to be at most two short sentences connecting public views, identifying an unanswered argument or inviting a suitable peer response; observe is appropriate when no invitation is useful. It cannot replace the speakers' provisional checkpoint. Formal presentation requires all speakers to confirm the same proposal. An applied current-version invitation survives an ordinary manual boundary, is included alongside any pending task and is addressed or its priority explained by the speaker. It preserves the original topic and does not dictate scope or a verdict. Configuration/input changes invalidate stale grants. Prompt brevity and semantic neutrality remain model behavior, not mechanical guarantees.

Only an explicitly selected judge can issue observe/speak/interrupt/mute/unmute/topic/pause/finish. This permits forced intervention and a unilateral ruling, with the existing provenance, limits, continuation and durable-storage gates. It does not imply participant agreement.

Exactly one speaker is generating at a time. In judge mode, at most one moderator call runs concurrently to monitor that speaker. Checks require new draft text, run at most once per 10 seconds, and are serialized with boundary decisions. The prompt defaults to observe, allowing incomplete reasoning to develop; intervention is for clear ongoing irrelevance or sustained repetition. Missing evidence, disagreement or an intended lookup is normally handled in the next exchange. A monitor can observe, interrupt, or mute the current speaker only; it cannot alter the next turn. A durable accepted stop decision revokes the current grant before aborting the owned turn. Scheduling waits for speaker and monitor cleanup; cleanup failure pauses or requires reconciliation. Finishing a speaker closes its draft boundary, so a delayed monitor result cannot affect the next speaker.

User stop remains authoritative and aborts the full runtime. Pause finishes the current answer and then stops. Boundary pauses recheck running status and cancellation inside the serialized commit lock, so a queued pause cannot overwrite a committed user stop. Moderator commands cannot change the original goal/constraints or user limits; a necessary change is a pause/request, followed by an explicit user configuration action. The application cannot prove a topic is semantically related; that constraint is stated in the moderator prompt and the full old/new/reason notification is reviewable.

Topic changes are two durable commits: notification with pending topic first, application at an idle boundary second. A crash/uncertain write between them cannot silently apply the topic. Explicit recovery, session reconstruction and pending-topic apply/discard are required. The original topic is retained in the history and becomes the default goal when no goal was supplied.

Judge finish records `authority=moderator`, result, dissent, unresolved and unhandled user requests; it is not unanimous consensus. Rooms without a judge (including ordinary facilitator rooms) require all configured speakers to confirm one proposal ID/taskVersion for `authority=participants`. No summary, silence or delivery receipt establishes completion. Manual execution pauses after N contributions for N configured speakers; interruption counts toward the bounded round. Judge decisions without speech are limited to 8 consecutive calls. Moderator call count is lifetime cumulative, default maximum 500, editable by the user while idle. Overall elapsed time is the union runtime duration, not the sum of concurrent calls. Reconstruction conservatively reserves outstanding prepared time and labels it uncertain budget.

Idle, version-checked Settings can change the moderator mode. Mode changes retire native sessions, preserve confirmed messages, clear proposal/outcome and do not start a turn. Switching to facilitator clears historical mutes. Journals omitting the field are read without rewriting; on their first explicit start with a moderator, the start commit records facilitator mode, retires old sessions and clears historical mutes. Previously saved rulings remain historical until the user explicitly reopens the discussion. An older strict-schema build may reject records containing the new field; preserve the matching data/build for rollback.

## Single-sentence response mode

New discussion/debate inputs may set optional `singleSentence: true`; omission or
false preserves ordinary replies without rewriting old journals. The choice is
fixed at creation, independent of manual/auto/conclusion scheduling, and is not
available for structured option evaluation. All AI turns, including moderator
openings, summaries, conclusions and peer reviews, use the same rule.

The public answer must be one nonempty paragraph and one sentence, without lists
or block formatting. `Intl.Segmenter` checks sentence boundaries after masking
URLs and common title/example abbreviations; it does not prove semantic brevity.
Prompts request one short main point without a hard character limit. Public prose
in control metadata must repeat the sentence or quote contiguous excerpts from
it: result, dissent, unresolved, delivery basis, review reasons/gaps, reference
reasons, moderator instructions and workflow prose cannot add another answer.
IDs, verdicts and source references retain their existing semantics.

Drafts are buffered and never emitted in previews, monitor input or failure
messages. After a complete, identity-valid answer fails the sentence check, the
same seat and native session get at most one correction with the original task
and permissions. The prepared call durably records `sentenceRewrite` (a distinct
provider request ID, reason, payload hash and character count) before that second invocation. Both attempts
share the original timeout, call ID, grant and contribution; usage is accumulated.
Only an accepted answer can advance response claims or conclusion review.
Repeated rejection saves the failed-call diagnostic, removes its session and
pauses without publishing the rejected text. Explicit continuation may try a new
turn; no third automatic invocation is made for the failed turn.

Pause requested before correction prevents it; pause during correction waits for
the current answer, and stop cancels immediately. Transport/cleanup failures,
invalid control identity and unconfirmed storage never trigger sentence retries.
Storage recovery retains its verification barrier and never replays a turn.
Older strict-schema binaries may reject these optional fields; rollback requires
the matching journal/build pair, not editing or stripping historical records.

## User attachments v1

Version 3 discussion/debate creation and user messages accept a multipart request
with one `payload` JSON field followed by up to five `files` fields. Existing JSON
requests remain supported. Selection and version 1/2 attachments are rejected.
Creation attaches files to the first public user message; subsequent messages may
contain attachments without text and retain their existing seat recipient.

Each file is limited to 10 MiB, with 25 MiB per request. Text extraction is limited
to 100,000 UTF-16 code units per file and 200,000 per request; overflow rejects the
whole input, never truncates. Strict UTF-8 and BOM UTF-16 text/code/CSV/JSON are
supported. PDF text retains page labels, DOCX extracts document text, and XLSX
includes worksheets (including hidden sheets), cell addresses, formulas and cached
results without recalculation. Images, charts and scans are not interpreted. Empty,
encrypted, unsupported and malformed documents fail without adding a message.

Parsing uses a terminable worker with a 30-second per-file deadline and a 256 MiB
V8 old-generation limit. Office ZIPs are checked for actual inflated size (100 MiB)
and entry count (10,000) before parsing. External resources and macros are not run.
The original remains unchanged; extracted text receives existing secret redaction.

Optional message `attachments` contain server-generated IDs, name, format, byte
and character counts, original/text SHA256, parserVersion=1 and warnings. Original
files and text live in the history directory's `attachments` child, outside journals,
events and performance data. Files are written and synced before the referencing
journal commit; an unknown journal outcome retains them and blocks scheduling.
Known pre-commit failures remove their unreferenced files. A process crash can leave
unreferenced files; they are preserved rather than guessed safe to delete, and the
discussion's permanent deletion includes all of its attachment files.

Retries use the existing discussion/message ID and compare ordered filename,
original hash and byte count with the normalized input. The server never accepts
client-supplied file paths or attachment descriptors. Visibility is filtered by
seat before text is loaded; moderators only get public attachments, and provider
identity never widens access. This works with research disabled and adds no tools
or filesystem roots. Incremental sessions receive attachments with their messages;
rebuilt sessions receive complete eligible history. Calls record ordered attachment
IDs and text hashes. Missing or changed content blocks the dependent call.

Authenticated `GET /api/discussions/:id/attachments/:attachmentId/original` forces
download; `/text` returns `{attachment,text}`. Both verify discussion ownership and
the requested content hash. JSON exports optionally add `attachmentContents`;
Markdown exports append attributed text and metadata. Exported text can include
private input, just like the existing owner-visible history export. Neither export
embeds original binary files. Old journals are read without modification; older
strict-schema builds may reject new fields, so rollback needs matching data/build.

## Compatibility and operations

### Conclusion delivery v1

New rooms record `room.deliveryVersion=1`. A proposed result carries `delivery:{status:complete|partial,kind:answer|disagreement|undetermined,basis:[...]}` alongside its existing result/dissent/unresolved. These fields describe the delivered answer; they do not require a domain, scenario, fixed discussion stages, stance, decision framework or public prose template. The original goal and subsequent user clarifications determine the answer and its depth. A requested plan, poem or other creative form remains a valid answer. A reasoned disagreement or justified inability to determine an answer can be complete; missing requested content is partial and must be named in unresolved. Judge finish has the same delivery requirement without inventing participant consensus.

Each peer confirmation includes `review:{adequate,reason,gaps}` against the exact proposal. Missing review data does not count as confirmation. Review gaps identify missing requested content that blocks acceptance of the delivery. Limitations or dissent already faithfully retained in a sufficient conditional answer belong in the proposal's unresolved/dissent fields, not review gaps. An inadequate review records the peer's review and asks the author to respond or revise. A contradictory review (adequate=true with nonempty gaps) remains unconfirmed and creates a technical repair for the same reviewer against the exact proposal ID. The reviewer must independently clarify acceptance with empty gaps or rejection with the blocking gaps; the controller never deletes gaps or infers acceptance. New substantive limitations require a revised proposal. This clarification uses the existing three-call repair budget, including when the reviewer says done or responds with none. Exhaustion in conclusion mode explicitly reports the unresolved contradiction; auto/manual retain their existing repair-exhaustion behavior. Every replacement gets a new proposal ID, empty peer reviews and only the author's confirmation. Optional `conclusionRequest.kind` distinguishes substantive review from technical repair. Ordinary review and revision do not consume repair attempts. A substantive review request gives its author one priority response: the author may revise the proposal or rebut the review. After a completed same-version response is saved, that request is cleared in the speaker-processing commit before applying any new action. A none response, including neutral control fallback, leaves the original proposal, negative reviews and missing peer confirmations intact; it never creates an outcome or interim result. Ordinary scheduling and deferred invitations can then proceed. A new technical repair request created by the response remains pending. Failed, indeterminate or stale-version responses and unconfirmed storage do not consume the substantive request. Within an explicit execution, each unresolved task-version/target/proposal repair episode allows three actual target-speaker repair calls; successful resolution resets the counter, and unrelated turns cannot consume it. Conclusion mode pauses after exhaustion with the saved answer and gaps available for explicit continuation. Auto/manual discard that unaccepted proposal/request, record `delivery-repair-limit` and continue subject to normal boundaries and budgets. A correction target is scheduled before an ordinary facilitator invitation. An invitation for a different speaker is retained at the same task version, without being overwritten by routine coordination, until correction finishes and that speaker can address it. Input/configuration changes still invalidate it. Older requests without kind are classified from their saved peer reviews. Full review gaps remain in the proposal payload, rather than being copied into a size-limited task. Review provenance must reference a completed same-version call owned by that peer. Model adequacy assessments and structured fields are not independent proof of semantic or factual correctness.

All-speaker confirmation means agreement on the delivered text, including an explicit account of differing positions; it never requires every speaker to adopt the same substantive stance. A confirmed partial result remains partial in the stored outcome, pause reason and UI. Stopping, exhaustion and provisional checkpoints never create a complete outcome. The conclusion page shows the delivered answer/basis/limitations first and collapses historical stages after an outcome; it does not promote the latest individual message to the final answer. Further substantive changes require a new proposal and new peer confirmation, not an unreviewed post-confirmation rewrite.

Execution mode determines what a fully reviewed participant result means. In conclusion mode it creates the final outcome and stops. In auto/manual mode it is appended to optional `room.interimResults` with the proposal ID/version, answer, delivery status, dissent, unresolved points, confirmations, peer reviews and unhandled user requests; the pending proposal is cleared. Auto continues useful contributions subject to user stop/pause, limits and available work; manual still waits after each speaker-count round. An explicitly selected judge retains its separate ruling authority in every mode. Interim results are visible and exported separately from final outcomes and provisional checkpoints; old task versions remain marked stale. Stored interim records require unique all-seat confirmation and completed same-version speaker-call review provenance, never moderator agreement or silence. New optional fields do not rewrite older journals; older strict-schema binaries may reject them, requiring a matching journal/build pair for rollback.

Old journals load without rewriting or retroactive delivery claims. Explicit discussion continuation enables delivery v1, clears an unchecked pending proposal and retires native sessions while preserving messages. Previously saved outcomes remain historical until explicitly reopened by user input. Summary calls do not upgrade or complete old outcomes. Older strict-schema binaries may reject these new fields: rollback requires preserving a matching journal/build pair.

### Active discussion policy v1

The browser creates new rooms with `discussionPolicyVersion: 1`. Existing version 3 journals and API creations without that flag retain that policy setting until the user explicitly enables it in Settings; moderator authority follows the separate mode contract above. Version 1/2 histories are unchanged. Prompts describe roles, the original topic/goal, evidence provenance and optional coordination metadata. They do not require a decision matrix, scenario template or predetermined conclusion. Speakers choose useful lines of inquiry, respond to peers and may revise positions. Pending personal questions do not themselves block useful independent analysis. Research remains opt-in; a disabled lookup must stay pending while other analysis remains possible. Ordinary facilitators receive the brief role/control prompt without the speakers' work-report instructions.

The optional control `work` report contains a provisional `checkpoint` (answer, reasons, dissent, unknowns, public sources), deduplicated `questions`, and `tasks` of kind `analysis`, `research` or `check`, plus `answeredQuestions`/`completedTasks` resolutions. Stable ASCII keys matching `^[a-z][a-z0-9_-]{0,79}$` identify entries; underscores and hyphens are accepted. Shared workflow metadata accepts completed public source IDs only, visible in the owned session snapshot or the current saved answer; private inputs and provisional drafts cannot be its sources. A question resolution requires a public user message. An assigned task completion requires that seat's public source; a research completion additionally requires an observed authorized tool/evidence operation in that call. These checks establish provenance, not relevance, understanding or factual truth. Duplicate keys or normalized equivalent question text reuse one entry; semantic paraphrases still depend on the model choosing existing keys. Each queue holds at most 20 entries, each report at most 10 changes. Invalid schema, provenance or capacity rejects the entire report without applying its claims, records a metadata diagnostic and preserves a public-analysis fallback; it does not pause an otherwise valid turn.

The answer, call diagnostic and workflow update commit together. Fatal core control errors and rejected optional claims are separate: optional claim failures never authorize extra response coverage, completed research, a proposal or peer confirmation, while an otherwise valid turn can continue. The diagnostics tab localizes metadata reasons without displaying rejected raw JSON; older fatal diagnostic codes remain supported. A plain completed answer is an analysis fallback, not invented synthesis or agreement. Explicit summaries update the conclusion tab without declaring completion. Checkpoints show their source messages, dissent, unknowns and stale task version; outstanding questions/tasks remain visible when execution pauses. Session/authority mismatches, indeterminate provider results and unconfirmed storage retain their blocking behavior.

An active-policy judge pause/finish redirects first to a runnable task, missing current-task speaker coverage, or an independent public peer check when more than one seat can speak. Redirects are bounded per execution to `max(3, speakerCount + 1)`; budget exhaustion preserves the checkpoint and pauses rather than generating indefinitely. Muted seats are excluded from dispatch. Without a judge, runnable tasks take priority and a necessary coverage/peer check can override a speaker's `done`, with at most three such fallback redirects per execution. A fully confirmed proposal becomes an outcome or interim result according to execution mode only after the remaining runnable work/check completes. A checked reference is a model claim; no heuristic proves that analysis is useful or a checkpoint correct. Manual round boundaries, user stop/pause, existing execution limits and storage barriers remain authoritative.

Idle version-checked Settings can enable this policy and toggle research/read-only roots for live Codex/Claude rooms. Changing permissions or enabling the policy retires native sessions, preserves confirmed history and does not start inference. Topic/goal/constraint changes clear old scheduled tasks and retain the prior checkpoint with a stale-version label. Existing questions remain reviewable. Research tools stay unavailable to the moderator itself.

New failure metadata uses `digestFormat: canonical-v1`, hashing JSON values with sorted object keys so compact event-message references cannot create an insertion-order mismatch during recovery. Unmarked older metadata still uses its original digest check. Conflicting content remains blocked; no existing journal is rewritten or automatically repaired. An older build may reject active-policy rooms, new call diagnostics or canonical failure metadata. Preserve journals and restore the matching pre-upgrade data/build for rollback; reverting executables alone is insufficient. Deterministic acceptance and the unrun live comparison are specified in [DISCUSSION_POLICY_EVAL.md](DISCUSSION_POLICY_EVAL.md).

Version 1/2 behavior is routed unchanged. Explicit `/upgrade-v3` creates a new ID with completed eligible source history, elapsed budget and source linkage in its first durable commit; cancelled targets are not retained as reply references. There is no separately committed empty room before history adoption. Source bytes and old sessions remain untouched. Upgrade defaults to moderator off. New room configuration is version checked. Recovery never automatically retries an uncertain provider call. Gemini/Grok inference, provider billing and live moderator behavior remain unverified; deterministic and browser fixtures cover the application contract only.

Seat IDs that differ from providers (`codex-2`) and `label` exist only in builds that include this contract. A previous build's strict schema rejects such records and reports them as storage issues; it never loads them partially. Records whose seat IDs equal their providers are read unchanged, so older rooms need no migration, and rolling back means reverting the code and not opening multi-seat records with the older build. Several real CLI sessions of one provider alive in the same room have not been exercised against live CLIs; only fake adapters cover them.
